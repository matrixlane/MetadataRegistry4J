# 数据源配置自动重启与友好进度设计

日期：2026-10-24
状态：已确认（2026-10-24）
关联 OpenSpec 变更：`datasource-auto-restart`

## 1. 背景与已确认范围

当前初始化向导保存数据源配置时，`DatasourceConfigService.saveConfig()` 只写入 `application-local.yml`；运行中的 Hikari、Hibernate、Flyway 与 `DatabaseEnvironment` 不会重建。前端仅设置 `restartRequired=true`，要求用户手工重启应用。

用户已确认采用**方案 A：常驻启动器托管自动重启**，并包含**新配置启动失败时自动恢复原配置**。首版范围明确限定为：

- Windows 单机个人版；
- 通过项目自带启动器运行后端；
- 只改变初始化向导的数据源配置生效方式；
- 系统设置中的数据源页面保留现有“保存后手工重启”行为；
- 直接运行 JAR、IDE、Maven、Windows 服务、Linux、Docker 等启动方式不在首版自动重启范围内，继续使用原有手工重启指引。

本变更不修改数据库表结构，不涉及 ISO/IEC 11179 元模型或迁移脚本。

## 2. 目标与非目标

### 2.1 目标

1. 非技术用户在向导中修改数据源后，只需点击既有的“下一步”，无需执行命令、编辑 YAML 或手工重启。
2. 页面以真实阶段展示“保存、重启、数据库准备、验证、恢复向导”，不使用虚假的百分比。
3. 重启期间不发生重复提交、网络错误提示刷屏或误触发“放弃初始化”。
4. 新配置启动失败、启动超时或运行配置核对失败时，启动器自动恢复旧配置并重新启动。
5. 页面刷新后仍能恢复重启等待状态；数据库口令不得进入浏览器持久化状态、重启状态接口或日志。
6. 自动重启完成后，前端必须确认后端已完全就绪且实际运行配置就是目标配置，不能仅以端口可连接作为成功依据。

### 2.2 非目标

- 不实现不退出 JVM 的数据源热切换或 Spring 上下文热重建。
- 不把系统设置页一并改为自动重启。
- 不增加常驻启动器对无重启请求的普通进程崩溃的自动拉起策略；首版只处理明确的数据源重启事务。
- 不引入新的前端依赖、PowerShell 测试框架或服务管理器。

## 3. 现状与影响分析结论

- `DatasourceConfigService.saveConfig()` 的影响分析为 LOW；现有调用包括系统设置/向导共用的控制器与单元测试。
- `InitWizard.vue` 的 `saveDbConfig()` 仅由 `nextStep()` 调用，影响分析为 LOW。
- `DatasourceConfigController` 现有三个端点可保持不变；新增的自动应用端点不改变现有 `PUT /api/v1/datasource/config` 契约。
- `/api/v1/startup/status` 在 `ApplicationReadyEvent` 后才返回 `ready=true`，覆盖 Flyway、ORM 与启动 Runner，可复用为“启动完成”信号。
- `backendStartup.ts` 已提供不带 Axios 错误提示的静默探测模式，可复用于重启等待。
- 当前 `start.bat` 通过独立 `javaw` 启动后端，没有常驻监控者；必须新增启动器托管层，不能仅让后端退出后依赖原脚本自动恢复。
- 当前向导的 `beforeunload` 与路由离开守卫按“离开即放弃初始化”处理，重启事务期间必须显式排除，避免刷新或离开导致错误调用 `abort`。

## 4. 总体架构

```text
初始化向导
   │  POST config/apply（携带客户端生成的 restartId）
   ▼
DatasourceConfigController
   ▼
DatasourceRestartService
   ├─ 校验：本机回环请求、个人版、受管启动器、无并发重启
   ├─ 备份当前 application-local.yml
   ├─ 复用现有连接测试与配置保存逻辑
   ├─ 写入 restart-request.json / restart-status.json
   └─ 返回 202 后异步、优雅退出当前 JVM
                         │
                         ▼
backend-supervisor.ps1（常驻）
   ├─ 等待被托管的旧进程退出
   ├─ 以相同 JAR、profile 和工作目录启动新进程
   ├─ 探测 /startup/status，并核对实际数据源
   ├─ 成功：写入 SUCCEEDED，清理备份
   └─ 失败/超时：恢复备份，重启旧配置并写入最终状态
                         │
                         ▼
初始化向导静默轮询
   ├─ /api/v1/startup/status
   └─ /api/v1/datasource/restarts/{restartId}
```

职责边界：

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| 后端自动应用服务 | 参数与权限校验、备份、配置写入、请求状态、运行配置核对、延迟退出 | 直接强制杀死进程、跨进程等待 |
| 常驻启动器 | 进程生命周期、启动超时、失败停止、备份恢复、最终状态落盘 | 解析业务表单、修改 JPA/Flyway 配置 |
| 前端 | 阶段展示、静默轮询、刷新恢复、终态处理 | 估算真实百分比、读写本地配置 |

## 5. 后端接口契约

### 5.1 查询自动重启能力

`GET /api/v1/datasource/restart-capability`

响应数据：

```json
{
  "supported": true,
  "reasonCode": null
}
```

仅当以下条件同时满足时 `supported=true`：当前为 PERSONAL、请求来自本机回环地址、启动器注入了有效控制目录且该目录可写。非受管启动方式返回 `supported=false` 和稳定的 `reasonCode`，前端走原手工重启流程，不将其视为系统错误。

### 5.2 保存并自动应用

`POST /api/v1/datasource/config/apply`

请求采用新 DTO，包含客户端生成的 `restartId` 与现有数据源配置对象：

```json
{
  "restartId": "客户端生成的 UUID",
  "config": {
    "vendor": "sqlite",
    "filePath": "~/.metadata-registry/data/metadata-registry.db",
    "edition": "PERSONAL"
  }
}
```

成功后返回 HTTP 202，数据仅包含 `restartId`。前端在发起请求前即保存非敏感恢复标记；即使 202 响应因进程退出而丢失，也能用同一个 `restartId` 查询结果。使用同一 `restartId` 重试且请求指纹一致时按同一重启事务处理；以相同 ID 提交不同配置时返回 409。

失败约束：

- 不受管启动、非个人版、非回环请求、已有非终态重启事务时，在写配置前拒绝；
- 连接测试或配置校验失败时，不创建重启事务，不退出应用；
- 备份、配置写入或请求文件写入失败时，不退出应用；已发生的配置写入必须恢复到操作前状态；
- 后端通过可测试的退出执行器延迟关闭 Spring 上下文并终止 JVM，确保先让 202 响应写出；单元测试替换该执行器，不实际退出测试进程。

### 5.3 查询重启状态

`GET /api/v1/datasource/restarts/{restartId}`

响应只含非敏感状态：

```json
{
  "restartId": "UUID",
  "state": "VERIFYING",
  "verification": "PENDING",
  "reasonCode": null
}
```

- `state`：`PENDING`、`STARTING`、`VERIFYING`、`ROLLING_BACK`、`SUCCEEDED`、`ROLLED_BACK`、`RECOVERY_FAILED`。
- `verification`：`PENDING`、`MATCHED`、`MISMATCHED`、`NOT_REQUIRED`。
- `reasonCode`：稳定的机器可读原因，如 `STARTUP_EXITED`、`STARTUP_TIMEOUT`、`CONFIG_MISMATCH`、`ROLLBACK_TIMEOUT`；不向浏览器返回异常堆栈、配置内容或口令。
- 当状态为 `VERIFYING` 且当前进程已就绪时，后端核对实际 `DatabaseEnvironment`/当前 JDBC 目标与请求中的脱敏目标标识。启动器依据 `MATCHED` 或 `MISMATCHED` 决定成功或回滚。
- 未知 ID 返回 404；终态状态在控制目录中保留，供刷新后的页面查询。

所有三个新端点沿用数据源控制器现有的未初始化/管理员守卫；首版写操作和状态查询额外限制为本机回环来源。回环判断只按字面 IP 处理，不做 DNS 反解。

## 6. 配置备份与控制文件协议

控制目录由启动器经环境变量注入，默认位于用户目录下，例如 `~/.metadata-registry/restart/`。目录中至少包含：

- `restart-request.json`：重启 ID、创建时间、请求指纹、脱敏目标标识、备份位置；不含用户名或密码。
- `restart-status.json`：重启 ID、状态、原因码、更新时间；不含 JDBC 地址、账号、密码或异常堆栈。
- 每事务备份文件：保存原 `application-local.yml`；若原文件不存在，使用明确的“原配置缺失”标记，恢复时必须删除新文件而不是留下空 YAML。
- `stop.request`：停止脚本写入的停止信号，防止启动器在用户主动停止后重新拉起后端。

约束：

1. 配置、请求和状态文件均先写同目录临时文件，再原子替换；不支持原子移动时才允许降级为替换移动。
2. 备份文件可能含数据库口令，只能位于当前用户配置目录，不进入仓库、接口、浏览器存储或日志；成功或回滚就绪后删除。
3. 同一时刻仅允许一个非终态事务；新事务可覆盖已完成的最后状态，但不能覆盖进行中的状态。
4. 后端只负责创建事务与核对配置；启动器是推进 `STARTING` 之后状态及执行恢复的唯一写入者，避免双写竞争。
5. 启动器发现上次遗留的非终态事务时，优先按“未完成操作”恢复备份，避免在配置归属不明时继续启动目标库。
6. 保存配置时必须同步写入目标方言对应的 ORM 映射资源：SQLite 使用 `orm/orm-sqlite.xml`，SQL Server 与达梦使用 `orm/orm-team.xml`。本机既有 SQL Server 配置显式指定 `orm/orm-team.xml`，沿用该映射会在 SQLite 上创建 `ext.` 模式表并失败，目标库无法建成。

## 7. 启动器设计

新增 `scripts/backend-supervisor.ps1`，由 `start.bat` 以后台方式启动。它使用固定的 JAR、`JAVA_HOME`、个人版 profile 与项目工作目录启动 `javaw`，并持有子进程对象，不再通过端口号猜测或终止其他进程。

### 7.1 正常重启

1. 等待当前子进程退出；若存在 `stop.request`，启动器退出且不重启。
2. 没有重启请求时也退出，保持现有“用户停止后端后不会被自动拉起”的行为。
3. 发现本次重启请求后写入 `STARTING`，启动目标配置进程。
4. 在目标启动超时时间内轮询子进程状态、`stop.request` 和 `/api/v1/startup/status`。
5. `ready=true` 后写入 `VERIFYING`，调用本次重启状态接口进行运行配置核对。
6. `MATCHED` 时写入 `SUCCEEDED`，清理请求与备份，并继续托管新进程；`MISMATCHED`、进程提前退出或超时则进入恢复流程。

### 7.2 自动恢复

1. 写入 `ROLLING_BACK`；仅停止本次由启动器持有且尚未退出的目标子进程。
2. 恢复备份；若备份标记表示原配置不存在，则删除本次新建的配置文件。
3. 以相同启动参数启动旧配置，等待 `/startup/status` 就绪；此轮不做目标配置匹配。
4. 旧配置就绪后写入 `ROLLED_BACK` 并清理事务文件，继续托管旧配置进程。
5. 旧配置仍无法启动或恢复超时时，停止未就绪的目标子进程、写入 `RECOVERY_FAILED` 并保留备份供支持诊断，不进入无限重启循环。

目标启动与恢复启动默认各等待 180 秒，并允许启动器参数在测试中缩短。浏览器总等待时间必须覆盖两次启动及余量，且不得把启动器的恢复过程误报为“已经失败”。

### 7.3 启动与停止脚本

- `start.bat` 的后端启动分支改为启动常驻启动器；前端 Vite 启动、端口占用检查和现有 JDK/JAR 检查保持兼容。
- 启动器启动时清理旧 `stop.request`，再处理未完成事务。
- `stop.bat` 先写 `stop.request`，再停止后端与前端，确保停止操作不会被自动重启抵消。
- 运行日志按重启 ID 保留必要的启动器事件与进程退出码；不得在日志中记录配置内容或命令行中的敏感参数。

## 8. 前端交互与状态恢复

### 8.1 入口与能力降级

- 数据库步骤仍只有一个“下一步”前进入口，不增加第二个保存按钮。
- 当用户修改参数且连接测试已通过时，若 `restart-capability.supported=true`，调用自动应用接口；否则调用现有 `PUT /datasource/config` 并显示原手工重启说明。
- 自动重启前在页面内用简短文字说明“系统将自动应用设置并暂时离线，完成后会回到本页”，不增加技术细节或额外命令。

### 8.2 进度展示

自动应用后，以进度卡片替换数据库表单和底部导航，禁用重复操作。阶段如下：

| 阶段 | 进入依据 | 用户文案示例 |
| --- | --- | --- |
| 设置已保存 | 自动应用请求已受理，或已知该 ID 的事务存在 | “数据库设置已保存” |
| 正在重启应用 | 等待旧进程退出与新进程就绪 | “正在应用设置，应用会暂时离线” |
| 正在准备数据库 | 启动探针已可达但尚未 ready，或启动器处于 STARTING | “正在准备数据库，首次使用可能需要几分钟” |
| 正在确认并恢复 | ready=true，等待配置核对与终态 | “正在确认设置并恢复初始化向导” |
| 完成或已恢复 | 收到 SUCCEEDED 或 ROLLED_BACK | “设置已生效” / “已恢复原数据库设置” |

- 精确耗时不确定，使用不确定状态的旋转指示、已完成/当前阶段和已等待时间，不显示编造的百分比。
- 使用具有可访问名称的原生 `progress` 不确定状态元素或现有同等语义组件，并通过 `role="status"`/`aria-live="polite"` 宣读阶段变化，不抢夺键盘焦点。
- 尊重 `prefers-reduced-motion`，减慢而非完全停止活动指示。
- 所有轮询使用裸 `fetch` 或既有静默机制；连接拒绝、请求中止和暂时 5xx 是重启期间的预期状态，不弹 Axios 全局错误提示。

### 8.3 刷新、离开与终态

- 发起请求前，在 `sessionStorage` 保存 `restartId`、所选版本、恢复步骤和开始时间；不保存数据库密码、完整 JDBC 地址或其他凭据。
- 页面挂载时发现未终态标记，恢复到数据库步骤并继续轮询；刷新期间不触发“放弃初始化”确认或 `abort`。
- 重启事务期间的路由离开守卫不得调用 `abort`；阻止会干扰等待的导航，但不阻止用户关闭浏览器，服务端重启/恢复仍继续完成。
- `SUCCEEDED` 后清理标记、重新加载当前数据源与初始化状态，回到数据库步骤并显示成功；用户确认当前数据源后继续下一步。
- 若目标数据库本身已经初始化，则按现有路由规则进入应用，而不是强行再次显示初始化向导。
- `ROLLED_BACK` 后清理标记、加载旧配置并返回可编辑表单，显示：“新数据库设置未能应用，已恢复原设置，请检查后再试。”可提供“查看原因”，但仅展示友好的原因说明。
- `RECOVERY_FAILED` 或浏览器等待超过启动器两轮恢复窗口时，停止无限等待，显示“自动应用后暂时无法连接”，提供“重新尝试连接”；仍失败时给出重新打开应用与联系支持的明确指引，不要求用户手工编辑配置。

## 9. 安全、并发与数据保护

- 自动应用只接受 PERSONAL、本机回环、受管启动器和有效初始化场景请求；未初始化的远程客户端不能利用新端点重启服务。
- `restartId` 使用 UUID，服务端校验格式并防止不同配置复用同一 ID。
- 新接口不返回配置备份、目标 URL、用户名、密码、命令行或堆栈。
- 退出执行只针对当前 JVM；启动器只停止自己创建的子进程，不通过端口进行模糊 kill。
- 配置保存完成前不退出旧进程；目标配置验证成功前不删除旧配置备份。
- 不对目标数据库做删除、清空或“重试时重建”处理。若新 SQLite 文件在失败尝试中已产生部分结构，不自动删除该文件；界面提示用户检查或更换路径，避免误删已有数据。

## 10. 测试策略（TDD）

### 10.1 后端单元/切片测试

先写失败测试，再实现：

- 受管个人版自动应用成功：备份、配置写入、请求状态、202 与延迟退出调用顺序正确。
- 非受管、TEAM、非回环、并发事务均在写文件前拒绝。
- 连接测试失败无配置变化；配置/请求写入异常时恢复原文件，且不调用退出执行器。
- 相同 ID 与相同请求指纹幂等；相同 ID 不同配置返回 409。
- 状态查询的未知 ID、终态、配置 MATCHED/MISMATCHED，以及响应不含敏感字段。
- 原 `saveConfig()` 与系统设置页手工重启行为保持兼容。

### 10.2 启动器验证

不引入 Pester 等新框架，使用 PowerShell 自带解析器做语法检查，并以隔离控制目录、隔离配置和测试端口执行真实进程验证：

- 启动器启动后记录 PID；自动应用完成时旧 PID 退出、新 PID 不同且端口恢复。
- SQL Server 隔离临时库切换到全新 SQLite，最终 `ready=true`、当前配置为 SQLite，并可继续 `setup`/`commit`。
- 使用“连接可建立但结构不兼容”的 SQLite 副本制造启动失败，验证自动恢复旧配置、旧进程可用和 `ROLLED_BACK`。
- 通过缩短启动器超时模拟启动超时，验证不会无限等待或无限重启。
- 停止脚本在重启期间执行后，启动器和后端均退出，不发生再次拉起。
- 全部验证使用 `scratch/`、副本库和测试端口，不修改真实 SQL Server 库或用户正在使用的 SQLite 文件。

### 10.3 前端测试

为重启状态机/轮询工具和进度组件补充 Vitest，并覆盖向导接线：

- 保存受理、网络中断、ready=false、ready=true、配置核对、成功恢复的完整序列。
- 重启期间无全局错误 toast、无重复提交、底部按钮不可操作。
- 刷新后按 `sessionStorage` 恢复；存储内容不含密码；重启期间不调用 `abort`。
- `ROLLED_BACK` 返回可编辑表单；`RECOVERY_FAILED` 与浏览器超时提供重试。
- 不支持自动重启时仍走原手工重启流程。
- 不确定状态可访问名称、礼貌宣读和减少动态效果偏好。

- Web 模块相关测试及标准 Maven 回归命令。
- UI Vitest、类型检查与生产构建。
- 真实 `start.bat` 支持路径的端到端验证，而非只调用服务方法或模拟进程。

## 11. 验收标准

1. 在受支持的 Windows 启动器下，用户从 SQL Server 改为 SQLite 后无需任何手工重启，页面自动完成等待并回到可继续的初始化流程。
2. 用户只看到可理解的阶段与等待时间，不需要理解 JVM、YAML、Flyway 或进程概念。
3. 新配置无法启动时，系统自行恢复旧配置；用户能够继续检查并修改，不会被永久卡在“请重启”页面。
4. 重启期间刷新页面不会丢失等待状态、放弃初始化或暴露数据库口令。
5. 非受管启动方式与系统设置页的既有行为不回归。
6. 所有真实验证均在隔离环境完成，且最终交付通过项目标准构建、测试与端到端场景。

## 12. 已否决方案

- **后端临时重启助手**：进程分离、异常退出与恢复责任不如常驻启动器稳定，否决。
- **Spring 上下文内热切换**：需要重建并重新绑定大量数据库相关单例，风险和范围远超本需求，否决。
- **只自动执行停止/启动脚本而无状态协议**：无法区分端口可达与数据库真正就绪，也无法可靠回滚和恢复页面，否决。

## 13. 评审补强（2026-10-25）

代码评审后发现并修复的语义缺口，补充到本设计与 OpenSpec 规范中。

### 13.1 受理前的环境变量覆盖检查

保存后的数据源配置以 `${DB_URL:默认值}` 形式落盘，而环境变量优先级高于本地配置文件：机器上若已设置 `DB_URL`、`DB_VENDOR`、`HIBERNATE_DIALECT`、`DB_DEFAULT_SCHEMA`、`FLYWAY_SCHEMAS`、`FLYWAY_DEFAULT_SCHEMA` 且取值与默认值不同，重启后应用仍会用旧目标，用户只会看到"未能应用并已恢复原设置"这种无法定位的提示。

因此在受理自动应用时，服务端读取刚保存的配置，解析其中的占位符默认值并与环境变量实际值比对；存在冲突时**在写入配置之前**拒绝请求，并指明冲突的环境变量名称。

### 13.2 响应写出后再退出进程

旧实现由服务层在返回受理结果后自行调用退出执行器，响应可能尚未写完就被中断，浏览器侧会表现为"请求失败"，进而触发与真实失败无法区分的重试。改为由 `DatasourceRestartExitFilter` 在过滤器链结束后接管：仅当路径为自动应用接口且响应状态为 202 时，先 flush 输出缓冲，再调度退出。切片测试通过 `ObjectProvider` 取执行器，避免 `@WebMvcTest` 缺少 bean。

### 13.3 启动器存活校验

后端进程内的 `MDR_RESTART_SUPERVISED` 环境变量可能在启动器被强杀后仍然存在，此时后端会自称受管，但退出后没有任何进程负责拉起它。能力判定改为读取启动器写入的 PID 记录，核对进程存在、进程名与可执行路径一致；记录缺失或不可解析一律视为"没有启动器"，自动重启能力不可用。

### 13.4 事务失败后保持系统可用

原实现中，事务无效、目标启动失败或旧配置恢复失败都会让启动器直接退出，其 `finally` 又会停止后端，系统因此停在"已停止"状态。改为：

- 事务无效或恢复失败时，先写入 `RECOVERY_FAILED` 终态，再以磁盘上现有的配置重新拉起后端并继续托管；
- 启动器自身发生异常时保留仍在运行的后端，不连带停止可用系统；
- `RECOVERY_FAILED` 时保留请求文件（它是诊断与"遗留事务先恢复"路径的输入），仅 `SUCCEEDED`/`ROLLED_BACK` 才删除。

### 13.5 启动器互斥、遗留进程与备份清理

- 同一控制目录只允许一个启动器实例：未获得互斥体时写出 `supervisor.error` 标记并退出，`start.bat` 据此提示"自动重启不可用"；未获得互斥体的实例不得触碰控制目录中的任何进程记录。
- 启动时**无条件**清理上次崩溃遗留、仍占用端口的受管后端；无法证明归属时只记录日志，不终止进程也不中断启动。
- 配置备份含明文口令：成功或恢复就绪后立即清理；恢复失败时保留诊断备份，但超过 7 天且不属于当前事务的备份在启动时删除。

### 13.6 前端失败态的会话保持与初始化状态判定

- 判定"目标数据库是否已初始化"必须使用**本次重新读取**的结果：`checkInitialized` 在后端不可达时降级返回 `true` 且保留旧缓存，直接使用其返回值会在探测失败时把用户误送到已初始化的首页。新增 `refreshInitialized()`，成功返回新值、失败返回 `null`，`null` 一律进入失败态。
- 失败态一律保留会话恢复标记（刷新后仍能接上同一事务），仅当后端确认事务不存在时清除并回到可编辑表单，提示"设置未提交到应用"。
- 回滚路径使用 `RECOVERING` 阶段（"正在恢复原数据库设置"），不得复用表示"设置已生效"的 `RESTORING`；成功路径的收尾阶段高亮停留在"核对设置"，"恢复"一段只属于回滚路径。

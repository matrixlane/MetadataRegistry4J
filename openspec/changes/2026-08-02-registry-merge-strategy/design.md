## Context

- 既有联邦能力（`registry-federation`/`merge-request`）已实现条目级增量合并：合并包格式、水位线、`item_link`、首次身份匹配、三方比对（以"上次并入的源端版本快照"为合并基）、事务性并入与回执。本变更在其上定义注册表层面的合并策略。
- 现状缺口已核对：`GenericItemCreator` 并入条目时用 `registrationAuthorityRepository.findAll().stream().findFirst()` 随意取本地第一个注册机构作为归属，既无 RAI 匹配也无来源标识保留。
- 与 `active-registrar-ownership` 的分工：本地路径归属冻结由该变更规约；本变更是归属变更的唯一通道，且冲突裁决人须为目的方注册机构的活动 Registrar。
- 标识模型：`ScopedIdentifier` 属于命名空间与条目，一个条目可持有多个命名空间下的标识；`IdentifierStrategyConfig` 按命名空间定义标识生成策略。二者均已存在，双标识无需新表。

## Goals / Non-Goals

**Goals:**

- 注册表合并以 RAI 一致为前置，迁移条目重新关联到目的方注册机构。
- 来源命名空间与来源标识原样迁移，目的方命名空间按策略生成新标识；条目双命名空间双标识，来源侧可溯源。
- 重迁移幂等：来源未变更跳过；来源单側更新覆盖目的方旧版本。
- 双侧更新构成冲突，由目的方 Registrar 裁决后方可完成迁移。

**Non-Goals:**

- 不做字段级编辑合并与删除传播（沿用 `merge-request` 既有约束）。
- 不改变合并包格式与传输通道（federation bundle v1 沿用）。
- 不实现 CLOUD 多租户；RAI 匹配按值比较，与部署版本无关。

## Decisions

### D1：RAI 一致性作为注册表合并前置

合并发起/接收时校验来源方与目的方注册机构的 RAI（organizationIdentifier 等 RAI 组成字段）一致；不一致直接拒绝。RAI 一致即视为"同一注册机构在不同实例的表示"，因此迁移条目重关联到目的方注册机构在语义上是归位而非易主。

### D2：归属重关联 + 双命名空间双标识

并入条目时：

- `registrationAuthority` 设为 RAI 匹配的目的方注册机构（替代 `findFirst()`）。
- 来源命名空间原样迁移到目的方（不关联注册机构；其 `namingAuthority` 记录真实来源机构，与 `active-registrar-ownership` 的外部命名空间语义一致）；来源标识（identifier 与 version）在该命名空间下原样写入。
- 同时在目的方命名空间下，按该命名空间的 `IdentifierStrategyConfig` 自动生成为条目生成新标识（identifier 与 version）。

迁移后条目持有两个 ScopedIdentifier：来源命名空间（来源标识 + 来源版本）与目的方命名空间（新标识 + 目的方版本）。

### D3：全局命名空间与命名空间全局标识映射

命名空间的跨实例身份不靠名称匹配，而靠"全局命名空间 + 共享 UUID 标识"：

- 每个注册表最多一个全局命名空间，专为迁移等"外交"任务存在，命名一眼可辨外部用途（如"全局命名空间"）；其标识策略为 UUID（`IdentifierStrategyConfig`），保证全局唯一。全局命名空间不关联注册机构、不用于普通条目注册。
- 命名空间作为被标识项：`Namespace extends Item`，以 Administered_Item 包装该命名空间（`IdentifiedItem.item` 指向它）后，方可在全局命名空间下挂接 Scoped_Identifier。
- 来源方发起迁移时，为待迁移命名空间（若无）在来源全局命名空间下生成 UUID 标识；目的方创建来源命名空间副本后，在目的方全局命名空间（单例，同一个）下建立 identifier 相同的 Scoped_Identifier。两侧命名空间的映射键即该共享 UUID。
- 一个目的方迁入多个来源方时，建立多个来源命名空间副本，全部复用同一个全局命名空间，各自持有不同 UUID 的 Scoped_Identifier（分别与各自来源方一致）。
- `ScopedIdentifier.identifier` 一经指派不可变（模型既有约束），保证映射长期稳定；条目迁移时来源命名空间的定位以该 UUID 为锚点（配合 D4 合并基）。

备选方案：按命名空间名称/URN 匹配。否决——名称可改、可撞名，无法"始终保持能匹配上"。

### D4：合并基与重迁移判定复用来源命名空间标识的版本

目的方上来源命名空间标识的 `version` 记录"上次迁移的来源版本"，即合并基；`item_link` 继续承担跨实例身份定位。

- 重迁移时：来源版本 == 合并基 → 跳过（幂等）；来源版本 > 合并基 且目的方命名空间标识版本未本地递增 → 干净更新，覆盖目的方旧版本并推进合并基。
- 目的方本地编辑会递增目的方命名空间标识版本（既有版本历史/版本递增机制）。

备选方案：在 `item_link` 上新增"上次迁移版本"列。否决——来源命名空间标识的版本天然承载该信息，避免冗余状态不一致。

### D5：冲突检测与 Registrar 裁决

冲突判定：来源版本 > 合并基（来源更新）且目的方命名空间标识版本相较上次迁移后递增（目的方本地更新）。示例：首次迁移后来源版本 10、目的方版本 1；目的方本地更新使目的方版本变为 2，来源方更新为 11 → 双侧变更 → CONFLICT。

冲突 MUST 由目的方注册机构的 Registrar（以其活动 Registrar 身份）裁决，整项裁决（采用传入 / 保留现有），裁决完成前本次迁移 MUST NOT 置为 MERGED。与既有"三方比对与冲突裁决""评审与事务性并入"要求衔接；评审人资格在合并策略语境下收紧为目的方 Registrar。

### D6：治理对象唯一化

RAI 匹配的注册机构在目的方只保留一份；注册规范、命名空间按既有"治理对象唯一化"方向归并（注册机构关联的命名空间与 RAI 命名空间匹配）。Scoped_Identifier 是否需要重新生成沿用既有可选项——本策略下目的方新标识一律重新生成（D2），来源标识一律保留。

## Risks / Trade-offs

- [来源命名空间在目的方无注册机构关联，可能被误认为普通外部命名空间] → 其 `namingAuthority` 记录来源机构；迁移来源可追溯，且该命名空间下条目归属仍为目的方机构。
- [目的方版本递增机制若在某些编辑路径未触发，冲突会漏判] → 实现时核对所有本地更新路径的版本递增；冲突检测以版本比较为准，辅以版本历史（version_history）佐证。
- [RAI 一致校验阻断了 RAI 不同的合法互认场景] → 这是明确的策略选择：RAI 不同的协作走条目级 `merge-request` 既有流程，不走注册表合并。

## Open Questions

- 治理对象唯一化的具体归并规则（注册规范、命名空间按什么键匹配）在实现期按既有"治理对象唯一化"方向细化确认。

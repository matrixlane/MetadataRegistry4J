## MODIFIED Requirements

### Requirement: 初始化向导中的数据库配置
数据库配置 MUST 作为初始化向导的独立步骤，紧随版本选择之后。`PERSONAL` 版 MUST 允许跳过该步骤，跳过时使用默认 SQLite 文件库；`PERSONAL` 版也允许配置 SQL Server 或达梦。`TEAM` 版 MUST 强制完成数据库配置（不得跳过），且 MUST NOT 提供 SQLite 选项。数据库配置的提交、连接测试、持久化与生效方式遵循 `datasource-configuration` 能力的规则。数据库配置完成（含选择"使用默认 SQLite"并继续）时，系统 MUST 记录数据源已确认并触发**一次自动重启**，数据库初始化 MUST 在该次重启过程中完成；用户 MUST NOT 被要求手工重启进程。

#### Scenario: 个人版跳过数据库配置
- **WHEN** 管理员在个人版向导的数据库配置步骤选择"使用默认 SQLite"并继续
- **THEN** 向导 SHALL 记录数据源已确认并触发一次自动重启，重启过程中完成数据库初始化，随后向导从后续步骤继续

#### Scenario: 团队版必须配置数据库
- **WHEN** 管理员在团队版向导中未完成数据库配置就尝试进入下一步
- **THEN** 向导 SHALL 阻止继续并提示必须先完成数据库配置

#### Scenario: 配置外部数据库后重启继续
- **WHEN** 管理员在向导中配置了 SQL Server 或达梦并通过连接测试
- **THEN** 系统 SHALL 持久化配置、记录数据源已确认并触发一次自动重启，数据库初始化在该次重启中完成，重启后向导从目标数据库重新评估状态并允许继续初始化

### Requirement: 提交语义

`commit` MUST 按部署版本差异化处理管理员密码：`TEAM` 版 MUST 校验管理员处于待设置密码状态、两次密码输入一致且长度合规（8-64 字符），随后持久化管理员密码哈希、写入 `system.edition` 并将 `system.initialized` 置为 `true`，且 SHALL 签发管理员会话令牌；`PERSONAL` 版 MUST NOT 要求或接受密码输入、MUST NOT 写密码哈希、MUST NOT 签发任何令牌，仅写入 `system.edition` 并将 `system.initialized` 置为 `true`（个人版无登录概念，密码状态保持待设置占位）。两种版本的提交响应 MUST 区分是否携带会话令牌。提交后 `abort` MUST NOT 再清除业务数据。系统不存在注册表运行模式（SINGLE/MULTI）设置，初始化请求与状态响应 MUST NOT 包含 `runningMode` 字段。提交成功时系统 MUST 同步把本地初始化状态记录标记为已初始化，使"是否已初始化"的判定不再依赖数据库查询。

#### Scenario: 成功提交

- **WHEN** 管理员在 `TEAM` 版完成 setup（响应携带强制改密向导会话）后提交合法的新密码
- **THEN** 系统持久化密码哈希并完成初始化，后续登录须使用新密码

#### Scenario: 个人版成功提交

- **WHEN** 管理员在 `PERSONAL` 版完成 setup（响应无会话数据）后提交（无密码字段）
- **THEN** 系统完成初始化，应用立即可无登录使用

#### Scenario: 个人版提交携带密码被拒绝或忽略

- **WHEN** 调用方向 `PERSONAL` 版初始化提交中传入密码字段
- **THEN** 系统 MUST NOT 持久化任何密码哈希，按无密码提交处理

#### Scenario: 提交后调用放弃

- **WHEN** 系统已完成初始化，调用方请求 `abort`
- **THEN** 系统 SHALL 视为无操作，业务数据不受影响

#### Scenario: 提交后本地状态记录同步

- **WHEN** 初始化提交成功
- **THEN** 本地初始化状态记录 SHALL 标记为已初始化，且后续"是否已初始化"的判定 MUST NOT 依赖数据库查询

### Requirement: 未初始化访问控制保持
系统未初始化时，初始化向导相关端点、数据源连接测试端点与登录端点 MUST 保持匿名可访问；其余 API MUST 要求认证。该行为 MUST NOT 因数据库方言或部署版本不同而改变。"未初始化"的判定 MUST 依据本地初始化状态记录与必要配置的存在性，MUST NOT 依赖数据库查询；因此在数据库尚未配置完成时，访问控制判定 MUST NOT 触发任何数据库访问。

#### Scenario: 未初始化时访问业务接口
- **WHEN** 系统未初始化，未认证客户端请求业务 API
- **THEN** 系统 SHALL 拒绝该请求并返回未认证错误

#### Scenario: 判定未初始化不访问数据库

- **GIVEN** 本地初始化状态记录表明系统尚未初始化
- **WHEN** 未认证客户端请求业务 API 触发未初始化访问控制判定
- **THEN** 系统 SHALL 完成判定并拒绝请求，且判定过程 MUST NOT 访问数据库

### Requirement: 静态预置数据的统一定义与时机
系统 SHALL 将全部静态预置数据收敛到单一幂等入口 `StaticDataPresetService.presetAll()`，数据值仅以 SQL 预置脚本为数据源（2026-09-19 用户裁定：应用代码 MUST NOT 包含名称预置数据、不做运行时 Locale 解析）。静态预置集合 MUST 包含：G20 语言代码（22 条，固定 UUID）、语言中文名称与地区名称（22 条）、`identifier_strategy_config` 全局默认行（`UUID`/`INTERNAL`/`is_global_default=1`）、占位超级管理员（`admin` / `NO_PASSWORD`）、每注册机构的标准注册流转规则（调和语义，不覆盖用户定制规则）。`presetAll()` MUST 幂等：连续执行两次结果集不变。启动期的静态预置 MUST 作为数据库初始化引导的一个步骤执行，且 MUST 仅在引导此前的连接校验与迁移步骤成功后才执行；引导失败时 MUST NOT 执行静态预置，MUST NOT 使应用无法启动。

系统组织与系统默认命名空间均不再是预置数据：系统 SHALL NOT 预置 `sys:` 系统默认命名空间；历史系统组织（固定 UUID `00000000-0000-0000-0000-000000000001`）不再创建，存量库中无引用（命名空间 NamingAuthority、联系人所属组织）的历史系统组织行由数据迁移移除。用户可见的组织列表与组织下拉选项 MUST NOT 包含系统组织。

#### Scenario: 数据库设置完成后静态数据全部就绪
- **WHEN** 管理员在向导数据库步骤保存数据源配置并触发自动重启，重启过程中完成数据库初始化
- **THEN** 建表与迁移完成后，静态预置 MUST 在应用就绪前执行完毕，静态预置集合中的全部数据可用

#### Scenario: 幂等重复执行
- **WHEN** `presetAll()` 在同一数据库上连续执行两次
- **THEN** 两张语言表行数、全局默认策略、占位管理员均保持不变，不产生重复行

#### Scenario: 三方言一致
- **WHEN** 分别在 SQLite、SQL Server、达梦全新库上完成上述流程
- **THEN** 静态预置集合内容一致（方言差异仅限 SQL 语法与 schema 限定）

#### Scenario: 引导失败时不执行静态预置

- **WHEN** 数据库初始化引导在连接校验或迁移步骤失败
- **THEN** 静态预置 MUST NOT 执行，且应用 MUST 保持可运行并展示失败原因

### Requirement: 静态预置的三处执行时机复用同一入口
`presetAll()` MUST 在三处被调用且顺序一致：数据库初始化引导中（迁移之后）、恢复出厂设置清空后、初始化向导 `setup()` 清理用户数据后。初始化向导 `setup()` MUST NOT 直接写入任何静态预置数据（不得调用语言初始化、预置重放等步骤的旁路实现）；`FactoryResetService` MUST NOT 保留与统一入口不一致的预置序列。

#### Scenario: 恢复出厂后静态数据完整
- **WHEN** 管理员执行恢复出厂设置
- **THEN** 出厂完成后静态预置集合完整可用，且 `identifier_strategy_config` 全局默认行存在（含 SQL Server 方言）

#### Scenario: 向导 setup 不写静态预置
- **WHEN** 调用 `/api/v1/init-wizard/setup`
- **THEN** 请求处理过程中静态预置数据仅由 `presetAll()` 幂等兜底维护，`setup` 代码路径 MUST NOT 包含语言代码或语言名称的写入逻辑

#### Scenario: 启动期调用点归入引导

- **WHEN** 应用启动执行数据库初始化引导
- **THEN** 静态预置 SHALL 由引导步骤调用统一入口，且 MUST NOT 存在独立的第二处启动期调用路径

### Requirement: 全新 SQLite 库启动后可进入初始化向导

个人版使用全新 SQLite 文件库启动时，系统 SHALL 先创建当前应用数据库结构，再执行 Flyway 新库基线和静态预置，然后开放初始化向导状态查询。该流程 MUST NOT 依赖预先存在的数据库文件或手动导入基准库。基线之后的初始化 SHALL 使用既有 `setup`/`commit` 服务建立治理数据和完整注册项关联链。数据库结构创建 MUST 作为数据库初始化引导的步骤执行，失败时 MUST 报告原因而非使应用无法启动。

#### Scenario: 新检出无数据库文件时读取初始化状态

- **GIVEN** 本地 SQLite 数据库文件不存在
- **WHEN** 个人版应用启动并请求 `/api/v1/init-wizard/status`
- **THEN** 应用 SHALL 正常响应未初始化状态，SQLite 文件、schema、共同 Flyway 基线和静态预置均已就绪

#### Scenario: 新库完成初始化

- **GIVEN** 全新 SQLite 库的初始化向导可用
- **WHEN** 个人版执行 `setup` 后执行 `commit`
- **THEN** 系统 SHALL 标记为已初始化，且初始化生成的已标识条目满足受管链语义闭环

#### Scenario: 建表失败时报告原因

- **WHEN** 数据库初始化引导在创建数据库结构时失败
- **THEN** 系统 SHALL 报告失败原因并保持应用可运行，MUST NOT 以进程退出的方式结束

### Requirement: 遗留漂移库启动修复先于静态预置

启动期静态预置数据（`StaticDataPresetService.presetAll()`，含语言预置重放）执行之前，系统 MUST 先完成遗留漂移 SQLite 库的 `language_identification` 修复（若该库命中漂移签名，判定与修复语义见 `legacy-schema-repair` 能力）。修复器与静态预置的执行顺序 MUST 显式保证（修复先于静态预置），不得依赖 Runner 注册顺序的隐式行为。该顺序保证 MUST 使初始化向导的语言数据源在任何来源的库（全新库、迁移库、遗留漂移库）上均可用于向导治理配置。两者的执行 MUST 归入同一数据库初始化引导步骤序列。

#### Scenario: 遗留漂移库初始化向导语言可用

- **GIVEN** 一个遗留漂移 SQLite 库（`language_identification` 含 `language_id NOT NULL` 等遗留列，语言表为空）
- **WHEN** 应用启动完成（修复先于静态预置执行）并进入初始化向导
- **THEN** `/api/v1/languages` 返回 22 条内置语言（含 `zh-CN`"简体中文"），向导"文档语言"可选择

#### Scenario: 全新库顺序不受影响

- **GIVEN** 一个全新 SQLite 空库（引导的全新库路径）
- **WHEN** 应用启动完成
- **THEN** 修复器判定不命中直接跳过，静态预置按既有顺序执行，初始化流程与 sqlite-empty-db-bootstrap 行为一致

## ADDED Requirements

### Requirement: 启动相位与数据库行为边界

应用启动 MUST 按数据库配置是否被确认划分为相位。数据库配置未被确认时为**向导相**：应用 MUST NOT 建立任何数据库连接、查询任何表、执行任何迁移或数据脚本，连接池 MUST NOT 校验连接或补建连接，数据库初始化引导及其后续步骤 MUST 一律不执行。数据库配置已被确认时为**完整相**：应用 MUST 执行数据库初始化引导。相位判定 MUST 在应用上下文建立之前完成，并由同一判定结论驱动全部数据库相关行为。相位判定 MUST NOT 依赖数据库查询。

#### Scenario: 未确认数据源时零数据库行为

- **GIVEN** 本地初始化状态记录表明数据源尚未被确认
- **WHEN** 应用启动
- **THEN** 应用 MUST 正常启动并提供初始化向导可用，且启动过程 MUST NOT 建立数据库连接、查询表或执行数据脚本

#### Scenario: 已确认数据源时执行初始化引导

- **GIVEN** 本地初始化状态记录表明数据源已被确认且配置未被改动
- **WHEN** 应用启动
- **THEN** 应用 MUST 执行数据库初始化引导（连接校验、结构创建、迁移、预置），完成后开放就绪状态

#### Scenario: 配置被手工改动时退回向导相

- **GIVEN** 本地初始化状态记录中的数据源指纹与当前有效配置不一致
- **WHEN** 应用启动
- **THEN** 应用 MUST 以向导相启动并提示数据源配置已被手工改动、需重新确认，且 MUST NOT 带未知配置进入完整相

### Requirement: 初始化状态来源与既有部署一次性引导

"系统是否已初始化" MUST 以用户目录下的本地初始化状态记录为准，辅以数据库相关配置及其它必要配置是否存在，MUST NOT 以数据库查询作为常态判据。本地状态记录 MUST 原子写入，且 MUST NOT 包含数据库口令或完整连接串。既有部署（存在数据库配置但无本地状态记录）MUST NOT 被判定为未初始化：系统 MUST 在此类情形下**一次性**向数据库确认初始化状态并写入本地状态记录，此后 MUST NOT 再以数据库作为该判据。

#### Scenario: 本地状态记录驱动初始化判定

- **GIVEN** 本地初始化状态记录表明系统已初始化，且数据库配置存在
- **WHEN** 客户端查询初始化状态
- **THEN** 系统 SHALL 返回已初始化，且判定过程 MUST NOT 访问数据库

#### Scenario: 既有部署不被推回向导

- **GIVEN** 数据库配置存在但本地初始化状态记录缺失，且该数据库已完成初始化
- **WHEN** 应用启动
- **THEN** 系统 MUST 一次性确认该状态并写入本地状态记录，MUST NOT 推回初始化向导，既有业务数据 MUST NOT 被清除

#### Scenario: 既有部署确实未初始化

- **GIVEN** 数据库配置存在但本地初始化状态记录缺失，且该数据库尚未完成初始化
- **WHEN** 应用启动
- **THEN** 系统 MUST 一次性确认该状态并写入本地状态记录，随后按未初始化处理并开放初始化向导

### Requirement: 数据库初始化引导与失败语义

数据库初始化引导 MUST 由单一可重复调用的入口按序执行：连接校验、结构创建（仅全新库）、迁移或基线化、旧库修复、静态预置、标识符策略装载、治理数据回填。任一步骤失败时 MUST 记录失败阶段与可读原因并跳过后续步骤；应用 MUST 保持运行并展示"初始化系统失败"及原因，同时提供重试初始化与退出应用两个动作；用户既不重试也不退出时，应用 MUST 保持等待状态。启动期执行与运行期重试 MUST 复用同一入口。失败信息 MUST NOT 包含数据库口令或完整连接串。

#### Scenario: 引导失败时应用保持可用

- **GIVEN** 数据库不可达或结构不兼容
- **WHEN** 应用启动执行数据库初始化引导
- **THEN** 应用 SHALL 保持运行并展示"初始化系统失败"与可读原因，MUST NOT 以进程退出的方式结束

#### Scenario: 失败后可重试初始化

- **WHEN** 用户在失败状态下触发重试初始化
- **THEN** 系统 SHALL 复用同一引导入口重新执行，成功后恢复正常就绪状态

#### Scenario: 失败后用户确认退出

- **WHEN** 用户在失败状态下确认退出应用
- **THEN** 应用 SHALL 结束运行，且后续不得留下仍在运行的后端进程

#### Scenario: 失败信息不含凭据

- **WHEN** 检查失败信息、状态接口响应与应用日志
- **THEN** 其中 SHALL 不包含数据库口令、完整连接串或配置备份

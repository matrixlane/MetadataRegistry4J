## Why

2026-10-25 发生真实故障：用户运行启动脚本后应用无法启动，日志深处只有一句 `no such table: ext_language_identification`。根因是用户配置沿用 SQL Server 时代的 ORM 映射（`orm/orm-team.xml`）配着 SQLite 数据源，导致 ext 卫星表从未建出，而通用基线脚本依赖该表。

这次故障暴露的是一条被系统性违反的不变量：**在数据库配置完成之前，应用的启动链路里已经存在大量依赖数据库的行为**（空库探测裸连库、Flyway 迁移、Hibernate 建表、通用基线脚本、语言旧表修复、标识符策略装载、治理数据回填），连"用来修数据库的页面"本身（`/init-wizard/status` 与初始化拦截器）也依赖数据库判定初始化状态。其后果是：数据库一旦有问题，用户打不开那个本该用来修数据库的页面，且只看到一条深处报错；而"是否已初始化"这一事实每次请求都要查库，既慢又与数据库强耦合。

## What Changes

- **BREAKING**：启动引入显式的"相位"概念。数据库配置未被确认前，应用处于**向导相**，启动与运行**零数据库行为**——不建连接、不查表、不跑迁移、不执行任何 DDL/DML，连空库探测都不做。
- **BREAKING**：初始化状态判定不再来自数据库。改为以 `~/.metadata-registry/` 下的初始化状态文件（记录数据源是否已配置、配置指纹、是否已初始化）为准，辅以数据库相关配置是否存在；既有部署仅在状态文件缺失时**一次性**向数据库确认并补写状态文件，之后不再以数据库作为该判据。
- 数据库相关配置保存后，写入状态文件并触发**一次自动重启**；数据库初始化（连接校验 → 建表 → 迁移 → 预置）在该次重启过程中完成，向导随后自动续上。
- 启动期的数据库动作由隐式的自动配置/Runner 改造为**显式、有序、可捕获**的引导步骤：任一步失败即记录阶段与原因、跳过后续步骤，应用**保持运行**并展示"初始化系统失败"与可读原因，提供「重试初始化」与「退出应用」，等待用户确认退出。
- 数据源配置引入**指纹**：配置被手工改动时指纹失配，系统退回向导相并提示重新确认，而不是带着未知配置直接进入完整相。
- 上下文不再因数据库不可达而启动失败：连接池不再快速失败、实体工厂固定不执行建表、Flyway 自动配置改为程序化执行。

## Capabilities

### New Capabilities

（无。本变更不引入新的独立能力，相位与引导语义归入既有能力的扩展。）

### Modified Capabilities

- `system-initialization`: 初始化状态判定来源（数据库 → 本地状态文件 + 配置存在性）、启动相位的划分与各自的数据库行为边界、数据库初始化引导的步骤与失败语义、静态预置与治理回填的时机改为随引导执行。
- `datasource-configuration`: 数据源配置保存时同步写初始化状态文件与配置指纹；配置被手工改动时指纹失配的处理；配置确认与"一次自动重启完成数据库初始化"的衔接。
- `startup-readiness`: 就绪的判定改为由引导结果决定；就绪探针需能表达"初始化失败"及其原因；前端启动等待界面在失败态下不再无限等待。
- `registry-context-bootstrap`: 注册上下文回填纳入引导步骤序列，位置与静态预置、策略装载的先后关系明确化；引导失败时不执行回填且不阻断应用运行。
- `factory-reset`: 恢复出厂除清理数据库外，还须重置本地初始化状态文件，使系统回到未初始化状态。

## Impact

- **后端（metadata-registry-web）**：新增相位判定、初始化状态文件读写、数据库引导服务与失败态接口；改造 `FreshDatabaseInitializer`、`InitWizardService.getStatus`、`InitializationWizardInterceptor`、`StartupReadinessIndicator`、`DatasourceConfigService`；关闭 Flyway 自动配置并改为程序化执行；调整 Hikari 与 Hibernate 参数。
- **前端（metadata-registry-ui）**：初始化界面新增"初始化系统失败"状态与「重试初始化」「退出应用」动作；`/init-wizard/status` 契约扩展失败态字段。
- **脚本**：启动器与 `start.bat` 语义不变（引导失败时后端保持运行，与现有托管语义一致）。
- **数据**：新增用户目录下的初始化状态文件；不改变任何表结构、迁移脚本或基线数据内容。
- **风险**：建表路径从实体工厂创建期移至引导期（三方言需实测）；既有部署升级路径需保证不被迫重新初始化。

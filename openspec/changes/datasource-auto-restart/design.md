## Context

现有数据源保存只更新 `application-local.yml`，数据源、JPA、Flyway 和方言环境均在 Spring 启动阶段建立。全新 SQLite 库还依赖 `FreshDatabaseInitializer` 完成结构与基线初始化，因此不能通过刷新页面或更新几个运行中属性完成切换。

当前 `start.bat` 以独立 `javaw` 启动后端后结束，没有组件在后端退出后继续负责启动和恢复。已有 `/api/v1/startup/status` 只在 `ApplicationReadyEvent` 后就绪，可作为完整启动信号，但它不知道本次切换目标，也不承担进程托管。

已确认的部署边界为 Windows 单机个人版、项目自带启动器和初始化向导。详细用户需求见 `proposal.md`，阶段展示与恢复行为见对应能力 delta。

## Goals / Non-Goals

**Goals:**

- 用常驻启动器明确承担旧进程退出后的启动、超时和恢复责任。
- 将配置写入、重启请求、进程状态、目标核对和前端终态串成可恢复事务。
- 保留既有数据源保存 API、系统设置页和非受管启动方式行为。
- 让前端只根据可观察事实推进阶段，并能从刷新或响应丢失中恢复。

**Non-Goals:**

- 不实现 JVM 内热切换或通用 Spring 上下文重启框架。
- 不让启动器成为通用进程守护服务；无重启请求的普通退出不自动拉起。
- 不在失败时删除或重建目标数据库，也不支持跨机器远程重启。

## Decisions

### D1：由常驻 PowerShell 启动器托管进程，而非后端临时助手

新增 `scripts/backend-supervisor.ps1`，由 `start.bat` 后台启动。启动器持有自己创建的子进程对象，以固定 JAR、`JAVA_HOME`、个人版 profile 和工作目录启动后端，并等待明确的数据源重启请求。

选择理由：旧 JVM 退出后仍有独立组件执行启动与回滚；无需从当前 JVM 猜测完整命令行，也避免 Windows 临时 detached 进程的生命周期不确定性。启动器只停止自己创建的子进程，不使用端口模糊 kill。

备选：后端创建临时重启助手（进程分离与恢复可靠性较差）、Spring 上下文热重建（改造范围和风险过高），均否决。

### D2：新增自动应用端点，保留既有保存契约

新增：

- `GET /api/v1/datasource/restart-capability`
- `POST /api/v1/datasource/config/apply`
- `GET /api/v1/datasource/restarts/{restartId}`

`POST apply` 接收客户端生成的 `restartId` 和嵌套的现有数据源配置，成功返回 202。现有 `PUT /api/v1/datasource/config` 不变，系统设置页和非受管环境继续使用它。

选择理由：新流程需要事务 ID、备份和状态机，强行塞进旧 PUT 会模糊手工保存与自动应用语义，也增加兼容风险。

### D3：配置服务复用现有校验，自动应用服务负责事务边界

`DatasourceRestartService` 在写文件前检查 PERSONAL、本机回环、受管控制目录和非终态事务冲突；随后备份当前配置，复用 `DatasourceConfigService` 的连接测试、方言约束和配置生成逻辑，最后写入重启请求并调度退出。

配置生成必须随方言同步 `spring.jpa.mapping-resources`（SQLite → `orm/orm-sqlite.xml`，SQL Server/达梦 → `orm/orm-team.xml`）。本机既有 SQL Server 配置显式指定了 `orm/orm-team.xml`，若切换 SQLite 时沿用该映射，Hibernate 会尝试在 SQLite 上创建 `ext.` 模式表并失败，目标库无法建成。

配置及控制文件采用同目录临时文件加原子替换。备份、保存或请求写入任一步失败，都不退出旧进程，并恢复到操作前配置。退出逻辑封装为可替换执行器，生产实现延迟关闭 Spring 上下文并结束 JVM，测试不实际退出。

选择理由：连接测试和方言规则保持单一事实源；事务失败不能与数据库连接测试失败混为同一状态。

### D4：客户端预生成 restartId，重启事务幂等

前端在请求前生成 UUID 并保存非敏感恢复标记，再发送自动应用请求。后端持久化请求指纹：相同 ID、相同配置按同一事务处理；相同 ID、不同配置返回 409。

选择理由：即使 202 响应在旧进程退出时丢失，浏览器仍能凭原 ID 找到事务，不必盲目再次发起重启。请求指纹只保存散列，不额外复制凭据。

### D5：文件协议只承载控制状态，启动器单写运行时状态

控制目录由启动器通过环境变量注入，包含 `restart-request.json`、`restart-status.json`、每事务配置备份和 `stop.request`。状态为：

```text
PENDING → STARTING → VERIFYING → SUCCEEDED
                    └→ ROLLING_BACK ├→ ROLLED_BACK
                                    └→ RECOVERY_FAILED
```

后端创建 `PENDING`；启动器是 `STARTING` 之后状态的唯一写入者。终态保留用于页面刷新查询，新事务可覆盖终态，但不能覆盖非终态。启动器发现遗留非终态事务时先恢复备份，避免配置归属不明。

选择理由：浏览器无法直接读本地文件，而后端并非始终存活；由启动器持久化状态，任何后续可用后端都能报告最后结果。状态文件不包含 JDBC 地址、账号、密码或异常堆栈。

### D6：成功必须同时满足完整就绪与目标配置匹配

启动器先轮询 `/api/v1/startup/status`，确认 ORM、Flyway 和启动 Runner 全部完成，再进入 `VERIFYING`。重启状态服务读取请求中的脱敏目标标识，与实际 `DatabaseEnvironment` 和当前 JDBC 目标比较，返回 `MATCHED` 或 `MISMATCHED`。

只有 `MATCHED` 才能写入 `SUCCEEDED` 并删除备份；端口可达、HTTP 200 或单纯 `ready=true` 都不足以判定切换成功。

选择理由：防止旧进程尚未退出、误连其他实例或配置未按预期加载时被误判为成功。

### D7：目标失败自动恢复，但不清理目标数据库

目标进程提前退出、超过默认 180 秒未就绪或配置不匹配时，启动器停止自己持有的目标子进程，恢复原配置并重启。旧配置在独立 180 秒窗口内就绪后写入 `ROLLED_BACK`；恢复也失败则写入 `RECOVERY_FAILED`、保留备份并停止重试。

不删除失败尝试创建的 SQLite 文件，也不清空任何目标数据库。原配置不存在时通过显式标记区分，恢复应删除本次新建配置文件，而非留下空文件。

选择理由：配置可以安全恢复，数据库内容不能冒险自动删除；无限重启会让故障和日志不可控。

### D8：前端展示真实阶段，不伪造百分比

向导复用静默探测模式，依据请求受理、启动探针、重启状态和配置核对结果展示“设置已保存、正在重启、正在准备数据库、正在确认并恢复”。采用不确定状态活动指示、阶段文本和等待时间，配合可访问名称、礼貌宣读及减少动态效果偏好。

网络拒绝、暂时 5xx 和请求中止在重启窗口内按预期等待处理，不进入 Axios 全局错误提示。重启期间禁用重复提交和底部导航。

### D9：重启事务是初始化放弃语义的显式例外

发起请求前仅在 `sessionStorage` 保存 `restartId`、版本、恢复步骤和开始时间，不保存密码或完整 JDBC 地址。挂载时发现未终态标记则恢复数据库步骤并继续轮询。

重启期间刷新和路由离开不得调用 `abort`；刷新不弹“放弃初始化”。成功后重新读取数据源和初始化状态，回到数据库步骤；若目标库已初始化，则按现有规则进入应用。回滚后返回可编辑表单。

### D10：主动停止优先于自动重启

`stop.bat` 先写 `stop.request`，再停止前后端；启动器在普通等待、目标启动和恢复过程中都检查该信号。`start.bat` 启动时清理旧停止信号，再处理遗留事务。

选择理由：常驻启动器不能改变“用户停止应用就保持停止”的基本预期，也不能在停止后留下再次拉起后端的竞争。

### D11：首版额外限制为本机个人版，而非仅依赖现有匿名向导规则

自动应用和状态查询在既有数据源守卫之上增加 PERSONAL 与回环来源检查，回环只按字面 IP 判断，不做 DNS 反解。能力接口让前端在不受管环境中无错误地回退手工流程。

选择理由：未初始化端点现有匿名语义不能扩大为远程进程重启能力；明确能力探测比请求失败后再猜测启动方式更友好。

## Risks / Trade-offs

- [旧实例不是由新版启动器托管，首次升级后无法立即自动重启] → 能力接口返回不支持并保留手工流程；部署说明要求用新版启动器完成一次启动。
- [新库首次初始化可能较慢，固定超时可能误判] → 目标和恢复分别提供 180 秒窗口，启动器参数支持测试调整；浏览器等待覆盖两轮及余量，不提前宣告失败。
- [旧进程退出导致 202 响应丢失] → 客户端预生成 ID、提前保存恢复标记并以幂等事务查询结果。
- [失败目标库已产生部分结构] → 不自动删除；恢复旧配置并提示检查或更换目标路径，后续重试由现有启动兼容性逻辑处理。
- [备份包含数据库口令] → 仅放当前用户控制目录，不进入日志、接口或浏览器；成功和恢复完成后删除，恢复失败时仅为诊断保留。
- [启动器或机器异常终止留下非终态文件] → 下次启动先恢复备份，不盲目继续目标配置；状态原子写入降低半文件风险。
- [PowerShell 与批处理行为存在平台差异] → 首版只声明 Windows 支持；做语法检查和真实 `start.bat` 进程验证，不以单元测试替代端到端结果。
- [工作区存在并行基准初始化修改] → 实施时保留现有变更，按文件逐块合并；最终验证包含并行变更所需的构建与回归，不覆盖他人工作。

## Migration Plan

1. 构建并部署新版后端 JAR、前端静态资源和启动脚本，保持现有 `application-local.yml` 不变。
2. 通过新版 `start.bat` 启动一次，使后端处于受管状态；未受管的旧实例继续显示手工重启指引。
3. 首次自动应用时创建控制目录和事务备份，无需数据库或既有配置格式迁移。
4. 代码版本回退前，若存在非终态事务，先让启动器完成恢复或按备份还原配置；随后恢复旧 JAR、前端和脚本。旧版本会忽略新增控制文件，但不得保留一个仍在等待自动重启的前端任务。
5. 验证成功路径、目标失败恢复、恢复失败、刷新恢复和主动停止后，再按 OpenSpec 归档流程处理。

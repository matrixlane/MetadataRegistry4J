## Why

Metadata Registry 部署完成后，系统处于空白状态（仅有默认超级管理员账号）。为了让用户顺利开启数据治理工作，需要配置注册机构（Registration Authority）、注册管理员（Registrar）、组织（Organization）、联系人（Contact）及其对应的访问控制权限。虽然命名空间本身不是进行数据治理工作的必选项，但首先创建命名空间，然后开始数据治理工作，是最佳实践，因此向导中也推荐进行命名空间的初始化配置。

目前缺乏引导式的流程来串联这些步骤，管理员难以顺畅、有序地完成这套初始化配置。通过提供一个配置向导，可以降低系统的上手门槛，规范初始化准备工作，并确保后续数据治理工作的访问控制和规范性得到保障。

## What Changes

本变更将在前端和后端引入以下主要功能与修改：
1. **初始化引导向导 (Wizard UI)**：针对首次登录的超级管理员，提供单/多注册表运行模式选择、默认注册机构创建、注册管理员绑定、以及命名空间初始化引导。
2. **多模式运行支持 (Backend/Schema)**：增加系统运行模式配置（暂只启用单注册表模式，多注册表模式置灰不可用）。
3. **注册机构与管理员管理**：支持注册管理员（Registrar）与注册机构（Registration Authority）的绑定，以及基于父类 `Contact` 关联用户。
4. **命名空间与外部命名空间管理**：
   - 注册管理员可为注册机构创建命名空间（命名机构不可修改，默认为该注册机构）。
   - 注册管理员可删除命名空间（若存在关联的 `Scoped_Identifier` 则发出警示）。
   - 支持创建外部命名空间，其命名机构可关联外部组织（支持自动新建或选择已有组织）。
5. **组织与联系人批量配置**：
   - 支持注册管理员添加组织。
   - 支持批量导入/添加用户为联系人（Contact），为其设置所属组织及预定义角色（Submitter、Steward 等）。
6. **基于命名空间的细粒度权限控制**：
   - 实现组织和用户对命名空间的操作与访问权限控制。
   - 权限继承与覆盖规则：用户继承所属组织权限；组织无权限时默认只读所有命名空间；用户自定义权限覆盖组织权限；非联系人用户默认只读所有命名空间。
   - 无角色或非联系人用户在注册表内自动表现为只读。

## Capabilities

### New Capabilities
- `initialization-wizard`: 提供向导式初始化流程，引导超级管理员配置系统模式、创建注册机构与管理员，并完成命名空间、组织、联系人以及基于命名空间的细粒度权限设置。

### Modified Capabilities
- `system`: 更新系统核心模型与基础配置，以支持单/多注册表运行模式的存储、以及与 `Contact` / `Registrar` / `User` 的关联，并引入细粒度的命名空间权限验证拦截。

## Impact

1. **后端数据库与实体模型 (`metadata-registry-common-facilities` / `metadata-registry-web`)**：
   - 扩充/修正 `Contact`、`Registrar`、`RegistrationAuthority` 的关联关系，支持继承与用户绑定。
   - 新增命名空间权限配置表（例如 `NamespacePermission`），存储用户/组织对不同命名空间的读写权限。
   - 新增系统配置项以记录系统运行模式。
2. **后端服务与 API (`metadata-registry-web`)**：
   - 新增初始化向导相关的 Controller 与服务 API。
   - 拦截器或 AOP 增强：在命名空间、元数据项等接口中，集成细粒度权限校验逻辑（只读权限拦截写操作）。
3. **前端 UI (`metadata-registry-ui`)**：
   - 新增 `/init-wizard` 路由与对应向导组件。
   - 新增组织管理、联系人批量配置、命名空间权限设置等管理页面或对话框。
   - 调整前端路由守卫：检测系统是否已初始化，若未初始化且为超级管理员，则强制定向至向导页面。

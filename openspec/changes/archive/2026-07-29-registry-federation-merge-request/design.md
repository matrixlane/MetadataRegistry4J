## Context

典型场景：某员工在本机个人版实例上做了数周数据治理（新建/修订数据元素、值域、概念体系），之后希望周期性地把成果提交到所在团队的团队版实例，由团队负责人评审后并入，与团队既有成果合并。系统需要把这种关系建模为**联邦节点 + Git 式合并流**，而非一次性导入导出。

Git 概念到本系统的映射：

| Git | 本系统 | 现状 |
|---|---|---|
| commit log | `version_history`（item_id + version_number + snapshot_json） | 已存在 |
| remote | `registry_node` 对端节点登记 | 新增 |
| 跟踪引用（tracking ref） | `item_link` 跨实例条目链接 | 新增 |
| merge base | 上次合并快照（链接 + 水位线定位） | 由新模型推导 |
| PR / MR | `merge_request` + `merge_request_item` | 新增 |
| code review | 既有 `ApprovalService` 多级审批流 + `MatchingEngineService` 匹配确认 | 复用 |
| push（离线介质） | 合并包文件（zip） | 新增 |
| push（网络） | HTTP 推送 API | 新增 |

约束与前提：

- 依赖 `edition-aware-init-and-db-portability` 的版本概念与数据库可移植性规则（新增表必须 UUID 主键、不绑定 schema、双方言迁移）。
- 个人版与团队版实例是各自独立初始化的（无克隆关系），因此**首次合并没有合并基**，身份匹配是必经路径。
- 医院/企业内网场景下两节点可能网络不可达，文件包通道是必需而非可选。

## Goals / Non-Goals

**Goals:**

- 任意两个实例（PERSONAL→TEAM、TEAM→TEAM）可建立联邦关系并周期性执行"提交 → 评审 → 并入"循环。
- 每次提交只包含自上次成功合并以来的增量。
- 跨实例身份判定：自动匹配 + 评审人确认，链接一旦建立即可复用。
- 并入在目标库事务性完成，全程可追溯（版本历史 + 审批记录）。
- 文件包与 HTTP 两种通道共用同一包格式与处理管线。

**Non-Goals:**

- 不做删除传播（源端删除的条目不在目标端删除，仅记录提示）。
- 不做字段级手工编辑合并，冲突裁决粒度为"整项采用传入 / 整项保留现有"。
- 不做实例克隆、分叉（fork）与多上游拓扑。
- 不做云端租户节点联邦。
- 不实现自动合并（无人工评审的直接并入）。

## Decisions

### D1：全局逻辑身份 = 来源 RAI + 来源标识符

实例内 UUID 不具备跨实例意义。元数据项的全局逻辑身份由其来源注册机构标识（RAI 的 `organizationIdentifier`）与来源实例分配的 `ScopedIdentifier` 组成。合并包中每个条目携带该二元组与来源实例 UUID（仅供回执对照）。目标库中条目保留来源标识符作为外来标识，目标实例可按自身注册表规范另行分配本地标识符，两者并存。

备选方案：强制全网络统一 UUID（生成时全局唯一冲突协商）。否决理由：离线节点无法协商，且违背各实例自治原则。

### D2：`item_link` 作为跨实例跟踪引用

`item_link` 记录：`local_item_id`（本库条目）、`remote_node_id`（对端节点）、`remote_item_key`（对端逻辑身份：RAI + 标识符）、`remote_item_uuid`（对端实例 UUID，供回执）、`established_by_mr_id`（由哪个合并请求建立）、`established_at`。链接是双向可建立的：目标端并入时建正向链接，回执返回源端后建反向链接。链接一旦建立即后续合并的合并基定位依据。

### D3：首次合并走"匹配引擎 + 人工确认"

无链接条目的身份判定复用 `MatchingEngineService`：按标识符精确相等（置信度最高）、designation 相似度、结构特征给出候选匹配，在评审工作台以"匹配候选"呈现，评审人确认后建立链接。该流程与既有 `InteropMapping` 的 confirm/reject 工作流同构，UI 模式复用。

### D4：同步水位线与合并回执保证增量与可重复

`sync_watermark` 按（源节点, 目标节点）方向记录：`last_merged_at`、`last_merged_mr_id`、以及条目级基线由 `item_link` + 双方 `version_history` 推导。源节点计算增量：自水位线以来 `version_history` 中新建与变更的条目集合。目标端并入成功后直接更新自身水位线，并生成**合并回执**（receipt：MR 标识、并入条目对照表、目标端链接信息）；源节点凭回执（API 回调或回执文件导入）更新自身水位线与反向链接。回执丢失时源节点可重放同一合并包，目标端按条目幂等处理（已并入的相同版本跳过）。

### D5：三方比对与冲突裁决

对已建立链接的条目：合并基 = 上次并入时目标端记录的源端版本快照；源侧 = 当前版本；目标侧 = 目标库当前版本。仅源侧变 → 干净更新；仅目标侧变 → 跳过并提示；双侧均变 → 标记冲突，评审人整项裁决（采用传入 / 保留现有）。字段级编辑合并留待后续版本。

### D6：合并包格式（federation bundle v1）

zip 包，结构：`manifest.json`（格式版本、源节点 RAI 与节点标识、目标命名空间建议、水位线引用、条目清单与校验哈希）+ `items/*.json`（条目完整快照：标识、designation/definition、概念结构、值域、引用关系）+ `receipt-request.json`（回执投递方式）。包格式与传输通道无关：文件导入与 HTTP 推送解析同一管线。条目快照格式复用 `MetadataExportService` 的导出 DTO 并扩展来源身份字段。

### D7：评审复用审批流，并入事务化

合并请求到达目标端即创建 `ApprovalProcessInstance`（默认模板：团队负责人单级评审；可配置多级）。评审工作台按条目列出 ADD / UPDATE / CONFLICT / MATCH_CANDIDATE 四类及建议操作，评审人逐项裁决后整体批准。并入执行器在单事务内：应用条目写入（新建或更新）、写 `version_history`（`change_type=MERGE`，来源标注）、建立/更新链接、更新水位线、生成回执。任一条目失败整体回滚，MR 置为 FAILED 并附原因。

### D8：评审范围与权限

合并请求必须指定目标命名空间。评审人资格 = 目标命名空间上具备相应权限的账号（`namespace_permission`）或超级管理员。源端提交者身份以对端节点凭据 + 包内签署人信息表示，不要求源端账号在目标端存在。

### D9：与部署版本解耦

联邦能力不区分 PERSONAL/TEAM：任何实例都可作为源或目标。个人版默认仅配置文件包通道（无公网回调依赖）；团队版两种通道均可用。节点凭据采用预共享令牌（预置在对端节点登记中），不引入 PKI。

## Risks / Trade-offs

- [首次大批量合并的身份误匹配可能污染目标库] → 匹配候选必须人工确认才建链接；并入可整体回滚（事务 + MR 审计记录）；提供合并前"预演"（dry-run）报告。
- [回执丢失导致源端水位线停滞、重复提交] → 目标端按条目版本幂等跳过；支持手动导入回执文件补救。
- [评审工作台条目量大时可用性差] → 合并包大小限制与分批提交建议；列表按类别分组、支持批量裁决。
- [两侧标识符策略不同导致逻辑身份漂移] → 逻辑身份锚定来源 RAI + 来源标识符，目标端本地标识仅作别名，不参与身份判定。
- [审批流模板未配置的部署无法评审] → 联邦功能启用时自动创建默认单级模板。

## Migration Plan

1. 前置：`edition-aware-init-and-db-portability` 完成并验证。
2. 本变更按任务分组实施：节点与链接模型 → 包格式与增量计算 → MR 生命周期与文件通道 → 评审工作台与并入执行 → HTTP 通道与回执 → 双库端到端验证。
3. 全部为新增表与新增接口，无存量数据迁移；回滚仅需下架功能开关与新增表（无破坏性变更）。

## Open Questions

- 删除传播（tombstone）语义在元数据治理场景的产品定义（退役 vs 删除）待后续版本明确。
- 字段级合并与"编辑后接受"是否进入下一迭代。
- 多上游拓扑（一个个人版同时向多个团队版提交）当前模型可支持（水位线按节点对），但 UI 复杂度未评估。
- 合并包的签名与防篡改（内网传递介质不可信场景）是否引入轻量签名（HMAC + 预共享密钥）。
